# Minimum biclique cover contract

## Input

Each input is UTF-8 JSON with top-level keys `schema_version` and `instances`; `schema_version` is `minimum-biclique-cover-v1`. Each instance has keys `rows`, `cols`, and `ones`. `rows` and `cols` are the dimensions of a 0/1 matrix, and `ones` lists its 1-entries as arrays of the form $ [u, v] $ with $ 0 \le u < rows $, $ 0 \le v < cols $ and no repeated entry. Entry order carries no structural information.

## Required answer

Write `solution.json` in the output directory; the answer file must be a regular file written directly into that directory, and every other entry the solver leaves in the output directory must be a regular file or a real subdirectory. It must be strict JSON with exactly the top-level key `instances`, an array with one entry per input instance, positionally paired with them: the entry at index $ i $ is the answer for the $ i $-th input instance, and the array must follow the input order. Each entry has exactly the keys `rectangles` and `packing`.

`rectangles` is an array of all-ones rectangles; each rectangle is an array of two arrays: a list of distinct row indices in $ [0, rows) $ and a list of distinct column indices in $ [0, cols) $, both non-empty. Every cell formed by a listed row and a listed column must be a 1-entry of the instance, and every 1-entry of the instance must lie in at least one listed rectangle.

`packing` is an array of distinct 1-entries, each an array $ [u, v] $. Two 1-entries $ (u_1, v_1) $ and $ (u_2, v_2) $ lie in a common all-ones rectangle exactly when $ (u_1, v_2) $ and $ (u_2, v_1) $ are both 1-entries; no two packing entries may satisfy that condition. An all-ones rectangle that contains one packing entry cannot contain another, because it would contain both crossings, so a packing of size $ p $ forces every rectangle cover to use at least $ p $ rectangles.

The two arrays are required to have equal lengths, and that common size must be the minimum possible number of all-ones rectangles needed to cover the instance's 1-entries. With equal sizes the packing proves the lower bound and the rectangles attain it, which pins the optimum directly from the answer: a cover larger than its packing does not meet the requirement even though both parts may be individually valid.

## Input family and execution

Development instances are small matrices made of a few visibly separated all-ones blocks whose minimum equals the block count. The same description and the same optimum rule hold for the further small instance set staged at the public call. Additional instances are drawn from one declared structured family: a set of planted all-ones rectangles with pairwise incomparable row sets and pairwise incomparable column sets, together with further rows and columns shared among subsets of the rectangles; the 1-entries are the cells of the union of the planted rectangles, and the row and column labels are permuted, so nothing of the construction survives in the input. Every instance of the family carries a packing of one cell per planted rectangle, no two of which lie in a common all-ones rectangle, so its minimum rectangle count is exactly the number of planted rectangles. An input carries at most 4 instances, each with at most 60000 rows, at most 60000 columns and at most 2000000 1-entries, and each instance's minimum rectangle count (the rank bound every admissible answer must meet) is at most 60000. Every exercised input belongs to one of the two families described above.

The solver is invoked as `python3 /root/candidate.py INPUT_JSON OUTPUT_DIRECTORY`; the solver must work when the exact bytes of `/root/biclique_cover_submission/solver.py` are copied to `/root/candidate.py` and run as a single source file, and the public call starts in `/root/runtime/public` while the unseen call starts in `/root/runtime/heldout`. The submission must be one self-contained Python source file: a nonempty regular file of at most 4,000,000 bytes that does not depend on any sibling file in its submission directory, because only that one source file is copied and executed. The answer file must be readable within a 64,000,000-byte limit, far above every conforming answer. Each working directory and `OUTPUT_DIRECTORY` is fresh and writable. The solver must derive its answer from `INPUT_JSON`, create `solution.json` in `OUTPUT_DIRECTORY`, and terminate with status zero. Each invocation receives a fresh per-invocation scratch area for incidental files (the process's `HOME` and `TMPDIR` point there); the shared system temporary and world-writable directories (`/tmp`, `/var/tmp`, `/dev/shm`, `/dev/mqueue`, `/run/lock`) are not writable by the solver, and no scratch state survives between invocations. The solver runs with no network access and an empty stdin, so inputs are available only through `INPUT_JSON`; `/root/data/` (including this document) is a development-time aid and is absent when the solver runs. The solver may use the standard library, numpy 2.2.6, and scipy 1.15.3; the numerical libraries are restricted to a single thread. Each invocation must use at most 4 CPUs, a virtual address space of 8,589,934,592 bytes (RLIMIT_AS, so sparse mappings and library reservations count against it) and 8192 MB of memory in its container, and aggregate CPU time is capped at 14,400 seconds, four times the wall-clock limit. The solver must derive answers from inputs across five invocations sharing the budget: the public call, the unseen call, a call on an additional packaged instance set, and two calls on small instance sets generated at invocation time. The solver must also handle small instance sets generated at invocation time, within the same execution limits; each answer must be derived from the input it is given, not copied from another input's answer. Each invocation must finish within 3,600 seconds wall-clock, and the solver must complete every invocation, including validation of their results, within a combined wall-clock limit of 14,400 seconds total. The solver must meet every stated requirement for both development and unseen invocations, not just a subset.
